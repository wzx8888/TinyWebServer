## 0. 一页速览

12 个接口，4 张表，全部服务端渲染 HTML（无前端框架、无 JSON API）。

| # | 功能 | 接口 | 方法 | 登录 | 难点在哪 |
|---|---|---|---|---|---|
| 1 | 注册 | `/api/register` | POST | 否 | 表单解析要重写；重名判断有竞态；口令要散列 |
| 2 | 登录 | `/api/login` | POST | 否 | 明文存量账号怎么迁移；时序侧信道 |
| 3 | 登出 | `/api/logout` | POST | 否 | 清 Cookie 的属性必须与下发时一致 |
| 4 | 身份查询 | `/api/whoami` | GET | 否 | ——（会话机制的最小验证点） |
| 5 | 发帖 | `/api/article/create` | POST | **是** | 正文长度上限和 HTTP 层上限会打架 |
| 6 | 文章列表 | `/api/article/list?page=N` | GET | 否 | 分页在秒级时间戳下不稳定 |
| 7 | 文章详情 | `/api/article/detail?id=N` | GET | 否 | 浏览计数是写热点；评论排序同 6 |
| 8 | 发评论 | `/api/comment/create` | POST | **是** | 外键报错对用户无意义 |
| 9 | 关注 | `/api/follow` | POST | **是** | 联合主键拦不住"关注自己" |
| 10 | 取关 | `/api/unfollow` | POST | **是** | 幂等（没关注过也算成功） |
| 11 | 关注流 | `/api/feed?page=N` | GET | **是** | `ORDER BY` 跨 JOIN 会 filesort |
| 12 | 个人主页 | `/api/profile?id=N` | GET | 否 | 关注/取关按钮的状态 |

另有 2 个**保留的旧别名** `/3CGISQL.cgi`（注册）、`/2CGISQL.cgi`（登录）——存量页面
的表单 `action` 指向它们，删掉等于把这些入口变成 404，保留成本是路由表里两行。

一句话概括这批功能的性质：**它们都不是"加一个页面"，而是"让这个服务器第一次
具备承载业务的能力"**。下面第 1 节讲为什么。

## 1. 地基：为什么写业务前必须先补一层

面试官最可能问的第一个问题是"这看起来就是个 CRUD，难在哪"。答案在动手前读代码
得出的六个事实：

| 事实 | 位置 | 后果 |
|---|---|---|
| 没有真正的 CGI，`cgi` 只是"是不是 POST"的标志位 | `http/http_conn.cpp` 路由分发处 | 路由靠 URL 末段首字符硬编码，`0/1/2/3/5/6/7` 各占一个字符——**字符空间不够**，我要加 12 个接口 |
| 表单解析写死 `"user="` 的 5 字节 / `"&password="` 的 10 字节偏移 | 同上 | 只认这两个字段，完全无法复用 |
| 动态响应体只能走 `add_content()`，**超过 1024 字节静默失败** | `http/http_conn.h:42` 的 `WRITE_BUFFER_SIZE` | 表现为"连接莫名断开"，没有任何报错 |
| 连接池建连接时没设字符集 | `CGImysql/sql_connection_pool.cpp` | 中文乱码，且时好时坏 |
| 没有会话概念 | —— | 没有它做不了权限：所有写接口都能冒充他人 |
| 线程池在调 `process()` 前已取好一条连接挂在 `http_conn::mysql` | `threadpool/threadpool.h` | 业务代码**不能**再取第二条（池只有 8 条） |

第 6 条最反直觉：它意味着事务不能像教科书那样"自己再拿一条连接"——要么占满池子，
要么 `BEGIN` 和 `COMMIT` 落在两条连接上而**事务静默失效**（不报错，但数据不一致）。
所以 `db/transaction.h` 做成了强制复用那条预取连接的 RAII 包装。

**这段怎么讲：**"我花在补地基上的时间比写接口多。原项目是个很好的网络编程教学
项目，但它不是为业务设计的——路由地址空间只有一个字符、表单解析写死字节偏移、
动态响应有 1KB 硬上限。这三条不解决，第一个业务接口就写不下去。"

补出来的公共层：

| 文件 | 行数 | 解决上面哪一条 |
|---|---|---|
| `http/form_parser.{h,cpp}` | 148 | 表单解析（第 2 条） |
| `http/html_util.{h,cpp}` | 140 | HTML 转义，防存储型 XSS |
| `session/session_manager.{h,cpp}` | 286 | 服务端会话（第 5 条） |
| `auth/password.{h,cpp}` | 230 | bcrypt 散列 + 渐进迁移 |
| `db/sql_util.h` | 39 | SQL 字符串转义（utf8mb4） |
| `db/transaction.h` | 84 | RAII 事务（第 6 条） |

## 2. 逐个功能

每一节的结构是：**做了什么 → 关键实现 → 遇到的问题与解决 → 一句话讲法**。

### 2.1 注册

**做了什么：** `POST /api/register`，参数 `user` / `password`。成功后**直接建会话**
（不让用户注册完再登一次），返回 `/log.html`。

**关键实现：** `http/http_conn.cpp:1073` `handle_register()`

#### 问题 ①：表单解析完全不能用

原解析写死字节偏移，只认 `user=` / `password=`。任何新字段都要复制粘贴一遍偏移量。

**解决：** 写了通用的 `http/form_parser.{h,cpp}`（148 行），按 `&` 切分、
对键值做 URL 解码，并处理 `+` → 空格。这是后面**所有** 12 个接口的前提。

#### 问题 ②：重名判断的竞态

第一版按常规做法"先 `SELECT` 查有没有同名，没有就 `INSERT`"。这在并发下是错的：
两个请求同时查到"没有"，然后都插入。而且这个窗口**只在压测或真实并发下才出现**，
手工点两下永远复现不了。

**解决：** 给 `user.username` 加唯一键，**直接 `INSERT`，捕获 1062（`ER_DUP_ENTRY`）**。

```cpp
if (err == 1062) { LOG_INFO("register: username already exists: %s", name.c_str()); }
else             { LOG_ERROR("INSERT error(%u):%s", err, mysql_error(mysql)); }
```

把重名判断交给数据库的唯一约束——那是它本来就该干的活，而且比在内存里维护一份
用户名 map 可靠。同时 1062 记 `LOG_INFO` 而其他错误记 `LOG_ERROR`：**重名是正常
的用户输入，不是服务端故障**，不该污染错误日志。

> 顺带一个必须加的细节：`LOG_*` 宏展开后自带 `if`，所以上面这个 `if/else` 的
> 每层花括号**都不能省**——否则宏内部的 `if` 会把 `else` 抢走。这个坑我踩了两次。

#### 问题 ③：长度校验必须按字节，不能按字符

`user.username` 是 `VARCHAR(64)`。直觉上写"用户名不超过 64 个字符"，但 MySQL 的
`VARCHAR(64)` 在 utf8mb4 下是 **64 个字符**、最多 256 字节，而我在应用层用
`std::string::size()` 拿到的是**字节数**。一个中文字符占 3 字节，所以 85 个中文
字就超了列宽——**按字符数校验根本拦不住**。

**解决：** 统一按字节判断，并且**故意取得比列宽更严**（中文用户名最多 21 个字符）。
注释里写明了这个取舍："宁可少收几个字符，也不能让多字节输入撑爆列宽。"

> 这个坑当时的表现是"某些中文用户名注册后登录失败"——注册时插进去了（MySQL
> 对超长字符串在某些模式下会截断），登录时比对的是截断后的值。**根因是字符集
> 语义和应用层长度语义不一致**，不是某个 API 用错了。

#### 问题 ④：前端校验不算数

`root/register.html` 上有 `required` 和 `maxlength`。但接口是公开的，`curl` 直接
POST 就绕过去了。

**解决：** 服务端自己校验一遍，注释里写明"前端的 required/maxlength 只是体验"。

**一句话讲法：** "注册这个功能里真正的技术点不在注册本身，而在三件事：把写死
字节偏移的解析换掉、把重名判断从'先查后插'改成捕获唯一键冲突、以及意识到
`std::string::size()` 给的是字节而列宽算的是字符——中文用户会踩到。"

### 2.2 登录与口令存储

**做了什么：** `POST /api/login`，参数 `user` / `password`。成功建会话，返回
`/welcome.html`。

**关键实现：** `http/http_conn.cpp:1000` `handle_login()`，`auth/password.{h,cpp}`

#### 问题 ①：存量账号怎么迁到 bcrypt

原项目**明文存口令**（`user` 表就两个字段）。直接改成 bcrypt 面临一个现实问题：
库里已经有真实账号了，怎么迁移？三个选项：

| 方案 | 问题 |
|---|---|
| 一次性脚本批量转换 | 要停机；而且脚本拿不到明文，**谈不上"转换"** |
| 强制所有人重置口令 | 用户流失，且这是面试项目里毫无必要的破坏性操作 |
| **登录时渐进迁移** ✅ | 用户无感，不停机，不需要一次性脚本 |

**解决：** 登录请求按老路径校验明文，**通过后立刻把 bcrypt 散列写回**。

存储格式是自描述的（`$2b$10$` + 22 字符 salt + 31 字符散列），所以算法标识、
cost、salt 都在串里，将来调 cost 不需要改表结构。

#### 问题 ②：bcrypt 会静默忽略第 72 字节之后的内容

bcrypt 的输入上限是 72 字节，**超出部分被静默截断，不报错**。如果 HTTP 层允许
超过 72 字节的口令进到 `verify()`，就会出现"前 72 字节对得上就登录成功"，
等于把口令空间截短了。

**解决：** `PASSWORD_MAX = 64`，在 `verify()` **之前**就挡掉。同时带一个长度上限
还有第二个收益：bcrypt cost 10 单次约 60ms，用超长输入去跑完整散列是白送的
算力消耗。

#### 问题 ③：时序侧信道 —— 用户不存在时的那条快速路径

```cpp
MYSQL_ROW row = mysql_fetch_row(res);
if (row != NULL) { ... ok = password::verify(password, stored_hash); }
else             { /* 什么都不做 */ }
```

这段的自然写法会让"账号不存在"成为**只查一次表就返回**的快速路径，而"账号存在"
要付一次完整的 bcrypt（约 60ms）。攻击者不需要看返回码——**光看响应快慢就能把
哪些用户名有效列出来**。

**解决：** 用户不存在时也跑一遍同样代价的散列再丢掉结果：

```cpp
else { password::hash(password); }   // 结果没有用途，只要耗时对得上
```

#### 问题 ④：登录接口的 CSRF，`SameSite` 挡不住

写接口锁了 POST 并不能防 CSRF，跨站表单一样可以 POST——所以加了 `Origin`/`Host`
比对。但登录接口是个**例外**：登录不需要 Cookie 就能生效，而 Cookie 策略
（`SameSite`）管的是"要不要带 Cookie 过去"。所以对登录来说：

- `SameSite=Lax` **完全无效**（它保护的是携带 Cookie 的请求）
- 而登录 CSRF 的危害是"把攻击者的账号塞进受害者的浏览器"

**解决：** `origin_ok()` 这个守卫是**所有写接口**（含登录/注册）统一走的，不是
只挂在需要登录的接口上。这是"两套机制防的不是同一件事"的具体体现——`HttpOnly`
防 XSS 偷 Cookie，`SameSite` 防 CSRF，`Origin` 比对防的是 `SameSite` 覆盖不到的场景。

#### 问题 ⑤：换账号登录时，旧会话必须销毁

同一个浏览器先登 A、再登 B，如果不处理，服务端会同时留着两把有效的钥匙。

**解决：** `start_session()` 里**先销毁请求里带的旧会话，再发新的**
（`http/http_conn.cpp:969`）："让旧钥匙立即失效"是登录应有的语义。

**一句话讲法：** "口令这块我做了四件事：明文存量账号用**登录时渐进迁移**换到
bcrypt，不停机；`PASSWORD_MAX` 卡在 bcrypt 的 72 字节上限之下，因为 bcrypt 超长
会静默截断；用户不存在时补一次假散列，消掉'账号是否存在'的时序差；以及登录
也要过 `Origin` 校验——因为登录接口的 CSRF 危害是账号被塞给受害者，而 `SameSite`
对不需要 Cookie 的登录接口完全无效。"

### 2.3 登出与会话

**做了什么：** `POST /api/logout` 销毁服务端会话 + 清浏览器 Cookie；
`GET /api/whoami` 返回当前 `user_id`（未登录返回 `not logged in`）。

**关键实现：** `http/http_conn.cpp:1140` `handle_logout()`，
`session/session_manager.{h,cpp}`（286 行）

#### 问题 ①：清 Cookie 时属性写错，Cookie 就删不掉

```
下发时：Set-Cookie: SESSIONID=xxx; HttpOnly; Path=/; Max-Age=86400; SameSite=Lax
清理时：Set-Cookie: SESSIONID=;   HttpOnly; Path=/; Max-Age=0;      SameSite=Lax
```

**属性必须完全一致**（`HttpOnly` / `Path` / `SameSite`）。属性不一致时浏览器会把
它当成"另一个 Cookie"，原先那条**删不掉**——用户点了登出，服务端会话没了，但
浏览器还留着那个 ID，下次访问带着一个已失效的 Cookie。

> 这个问题的恶劣之处在于**它看起来是成功的**：服务端确实销毁了会话，日志正常，
> `whoami` 也返回未登录。只有抓 Set-Cookie 才能发现浏览器没删干净。

#### 问题 ②：会话清理需要一个单调序号，不能只靠 `time()`

会话有 TTL（24 小时）加容量上限（10 万条），超限时淘汰"最久未活动"的一条。
第一版直接用 `time()` 给 `last_active` 打时间戳。

**根因：`time()` 只有秒级精度。** 同一秒内建立的所有会话 `last_active` 完全相同，
"最久未活动"就退化成哈希表的遍历顺序——淘汰谁是不确定的。

**这不是理论问题**：表被撑满恰恰发生在**登录突发**的时候，而登录突发就是同一秒内
建一堆会话。

**解决：** 加一个单调递增的序号做无歧义的 tiebreaker。

**一句话讲法：** "会话这块有两个细节值得说：登出时清 Cookie 的属性必须和下发时
逐项一致，否则浏览器会当成另一个 Cookie、原值删不掉，而服务端的日志看起来一切
正常；以及淘汰策略不能只靠 `time()`——它只有秒级精度，而撑满会话表的正是同一秒
内的登录突发，退化成哈希遍历顺序就等于随机淘汰。"

### 2.4 发帖

**做了什么：** `POST /api/article/create`，参数 `title` / `content`。登录后
在列表页顶部直接有发帖表单，提交后 302 到详情页。

**关键实现：** `http/http_conn.cpp:1244` `handle_article_create()`

#### 问题 ①：动态响应超过 1024 字节会静默断连

原项目动态响应体只能走 `add_content()`，它写进一个 1024 字节的缓冲区
（`WRITE_BUFFER_SIZE`）。放不下就 `return false`，一路传到 `process_write`
返回 `false`，然后**连接被直接关掉**——没有日志、没有错误码。

一篇普通长度的帖子早就超过 1KB 了。所以这是写发帖功能时**第一个**撞上的墙。

**解决：** 动态内容一律挂到 `m_iv[1]` 上（`http/http_conn.h:157` 有注释说明），
不再走那个 1024 字节的写缓冲。

> **这是整份文档里最值得讲的一个坑**：它的表现（连接断开）和根因（写缓冲太小）
> 之间隔了三层调用，而且全程静默。**静默失败比报错更糟**——报错告诉你哪里错了，
> 静默失败只告诉你"没成功"。

#### 问题 ②：正文长度上限和 HTTP 层上限会打架

这是我在写这个功能时花了最久才想明白的一个约束。两个独立的上限：

- HTTP 层：`MAX_CONTENT_LENGTH = 49152`，超了返回 413
- 业务层：`CONTENT_MAX`，超了返回 400 + "正文太长"

看起来业务层随便设个 16000 就行。但正文在 HTTP 层是
`application/x-www-form-urlencoded`，**每个字节最坏会膨胀成 `%XX` 三个字节**
（中文、emoji、引号都会）。所以：

```
正文 16000 + 标题 255，编码后最坏 = 3×16000 + 3×255 + 约 20（分隔符）≈ 48785 字节
```

刚好落在 49152 之内。**如果 `CONTENT_MAX` 设成 20000**，一篇 2 万字节的中文长文
编码后会超过 48KB——用户看到的是 HTTP 层的 413，而不是那条"正文太长"的业务提示。
**两个限制打架了，用户拿到的是一个他看不懂的错误。**

**解决：** 按"编码后最坏膨胀 3 倍"反推 `CONTENT_MAX`，并把这段推导写进注释
（`http/http_conn.cpp:1207`）。任何后来改这两个常量的人都会看到"它们必须对得上"。

#### 问题 ③：为什么是 302 而不是直接渲染

发帖成功后如果用 200 直接渲染详情页，用户按 F5 会**重新提交一次表单**
（浏览器会重复最后一次 POST）。发帖是写操作，重复提交就等于连发两篇。

**解决：** 302 + `Location` 跳转到详情页（`redirect_to()`）。刷新时浏览器重放的是
一个 GET，安全。

> 顺带一个取舍：只有会改数据的接口才走 302，注册/登出返回的是 **200 + 渲染页面**
> （`serve_file`）。这个不一致在写冒烟脚本时把我坑过一次——我按发帖的 302 想当然，
> 结果 5 个断言全错。**先看代码再写期望值，别按"应该是这样"写。**

#### 问题 ④：`user_id` 只能来自 session

表单里可以放 `user_id` 隐藏字段——那样任何人改一个字段就能以别人身份发帖。

**解决：** `user_id` 一律从 `m_user_id`（session 解出来的）取，**请求参数里的
任何 `user_id` 都被忽略**。这条写成了业务层的"三铁律"之一：

```
1. user_id 一律取自 session（m_user_id），绝不从请求参数里读。
2. 字符串参数一律 sql_escape 后再拼进 SQL；数字参数一律 to_ll 转整数。
3. 渲染进 HTML 的用户内容一律 html_escape。
```

**一句话讲法：** "发帖功能里最能讲的是长度上限的推导：正文走
`application/x-www-form-urlencoded`，中文最坏膨胀 3 倍，所以业务层的 `CONTENT_MAX`
不能随便设——设大了，用户看到的是 HTTP 层的 413 而不是业务提示，两个限制打架。
我是从 49152 反推回 16000 的，并把推导写进了注释。"

#### 问题 ⑤：标题的 `maxlength` 漏了字节/字符换算 ⚠️ 尚未修

同一类问题的第三个位置，**而且这一条是我写这份文档时实测才发现的，当前代码里
仍然存在**。

发帖表单上写的是：

```html
<input type="text" name="title" maxlength="100" ...>
```

而服务端的 `TITLE_MAX = 255` 是**字节数**，`maxlength` 数的是**字符数**。
一个中文字符占 3 字节，所以 100 个中文字 = **300 字节 > 255**——
**浏览器放行，服务端返回 400。**

实测边界（`POST /api/article/create`，标题为 N 个「中」）：

| 标题 | 字节数 | 结果 |
|---|---|---|
| 84 个中文字 | 252 | 302（成功） |
| 85 个中文字 | 255 | 302（成功） |
| **86 个中文字** | **258** | **400「标题太长（上限 255 字节）」** |

也就是说，**中文用户在标题写到 86 个字时会收到一个 400，而前端从头到尾没有
阻止他**——表单在 100 字之前不会变红。

**这个 bug 值得讲的不是它本身（改一个 `maxlength` 就完了），而是它的位置。**
整个代码库里有前端长度限制的地方只有两处：

| 字段 | 前端上限（字符） | 后端上限（字节） | 换算后 | 一致？ |
|---|---|---|---|---|
| 评论正文 | `maxlength="330"` | `COMMENT_MAX = 1000` | 330 × 3 = 990 | ✅ |
| 帖子标题 | `maxlength="100"` | `TITLE_MAX = 255` | 100 × 3 = 300 | ❌ **超了** |

评论那一处我从 `1000 / 3` 正确推出了 330，标题这一处却直接写了 `100`——
说明当时靠的是"**这次记得换算**"，而不是一个能保证不遗漏的机制。

（用户名和口令的输入框**根本没有前端上限**，所以不存在这个矛盾；代价是中文
用户名超过 21 个字符时，用户只会拿到一个通用的 `registerError.html`，
看不出是因为"字节数超了"。这是同一根问题的另一副面孔：**约束存在，但没告诉
用户它在哪。**）

**修法：** `maxlength="85"`（85 × 3 = 255 字节）。但更该做的是把"字节上限 → 字符
上限"的换算做成**由同一个数派生的常量**，而不是在前后端各写一个数字——否则下一个
新增的表单字段还会漏。

> 本文档其余标注"实测"的结论都可以在 2 分钟内复跑验证；唯独这一条是**当前代码里
> 真实存在的缺陷**，不是历史记录。

### 2.5 文章列表与分页

**做了什么：** `GET /api/article/list?page=N`，每页 20 条，`JOIN user` 取作者名，
未登录也能看；登录后页顶多一个发帖表单。

**关键实现：** `http/http_conn.cpp:1291` `handle_article_list()`

#### 问题 ①：路由地址空间只有一个字符

原项目的分发靠 **URL 末段的首字符**：`0` 是注册、`1` 是登录、`2/3` 是 CGI、
`5` 是图片、`6` 是视频、`7` 是 `judge`。字符空间就这么几个，我要加 12 个接口。

**解决：** 换成**表驱动路由**——`map<string, Route>`，把"处理函数"和"是否只接受
POST"一起变成数据（`Route{handler, post_only}`），而不是散落在各个 handler 里的
`if (m_method == POST)`。

```cpp
static const map<string, Route> routes = {
    {"/api/article/list", {&http_conn::handle_article_list, false}},
    ...
};
```

附带收益是方法校验变成了统一的一处：写接口收到 GET 返回 **405 + `Allow: POST`**，
合法但未实现的方法（PUT/DELETE）返回 **501 + `Allow: GET, POST`**。这两个码的
区别是 RFC 语义，不是随便挑的。

#### 问题 ②：分页在秒级时间戳下是不稳定的 ⭐

这是这批功能里**最隐蔽**的一个 bug，而且只在大数据量或并发下才暴露。

`create_time` 是 `DATETIME`，**只有秒级精度**。连续发帖（或在压测下）很容易让一批
帖子的 `create_time` **完全相同**。此时"仅按 `create_time DESC` 排序"，在并列组
内部**没有定义顺序**。而分页是两次独立查询：

```
page=1: ... ORDER BY create_time DESC LIMIT 20 OFFSET 0
page=2: ... ORDER BY create_time DESC LIMIT 20 OFFSET 20
```

两次查询各自排序，并列组内部顺序一旦不一致，就会**有帖子在第 1 页和第 2 页各出现
一次，另一条帖子永远看不到**。

**解决：** 排序键补上唯一的 `article_id`，构成全序：

```sql
ORDER BY a.create_time DESC, a.article_id DESC
```

**代价为零**——而且这一点值得单独讲：InnoDB 的二级索引会**隐式带上主键**，
所以 `idx_create_time` 物理上就是 `(create_time, article_id)`，反向扫描恰好满足
`(DESC, DESC)`，不会多出 `filesort`。**加 tiebreaker 不但没变慢，还顺手修正了
索引的实际形态认知。**

> 同一个问题在评论列表（`ORDER BY c.create_time ASC, c.comment_id ASC`）和
> 关注流里各出现一次。**这是同一类 bug 的三次复现，根因是"秒级时间戳不是全序"。**

#### 问题 ③：不做 `COUNT(*)` 算总页数

第一版想显示"共 N 页"，于是加了一次 `SELECT COUNT(*) FROM article`。这是一次
**没有任何索引支撑的全表计数**，而且每次翻页都要再算一遍。

**解决：** 不需要知道总页数——**"当前页是否满 20 条"已经足够决定要不要给出
下一页链接**：

```cpp
if (n == FORUM_PAGE_SIZE) { /* 给下一页链接 */ }
```

省掉一次全表扫，代价只是最后一页恰好满 20 条时会多给一个指向空页的链接
（点进去显示"这一页没有内容"）。

#### 问题 ④：`?page=abc` 不能静默当成第 1 页

**解决：** 没给 `page` 时默认第 1 页，但**给了 `page` 而值非法**必须返回 400。
理由写进了注释："不能让 `?page=abc` 和 `?page=1` 返回同样的内容，那会把客户端
拼参数的 bug 藏起来。"

#### 问题 ⑤：巨大的 `OFFSET` 是一种廉价的 DoS

`?page=99999999999` 会让 `OFFSET` 变成一个巨大的数，数据库被迫**扫全表再丢弃**。

**解决：** `FORUM_MAX_PAGE = 100000` 卡住上界（同时保证 `page × 20` 不会让
`long long` 溢出）。

**一句话讲法：** "列表页是这批功能里唯一有算法味的地方。分页的正确性依赖排序是
**全序**——而 `create_time` 只有秒级精度，连续发帖时一批帖子时间戳相同，并列组
内部顺序未定义，于是会出现帖子在两页各出现一次、另一条永远看不到。修法是补
`article_id` 做 tiebreaker；而因为 InnoDB 的二级索引隐式带主键，`idx_create_time`
物理上就是 `(create_time, article_id)`，**加上去反而正好匹配索引，没有额外排序开销**。"

### 2.6 文章详情（浏览计数 + 评论列表）

**做了什么：** `GET /api/article/detail?id=N`，展示标题/作者/时间/正文、评论列表、
评论表单，并给 `view_count` 自增。

**关键实现：** `http/http_conn.cpp:1402` `handle_article_detail()`

#### 问题 ①：文章不存在时不能返回空白页

**解决：** 明确返回 **404 + 一页说明**。注释写明了理由："空白页会让用户以为是前端
渲染坏了，而实际是 id 错了。"

> 而且**没有**复用 `process_write` 里那个 `NO_RESOURCE` 的静态文案——那句是
> "The requested file was not found on this server."，是给"静态文件找不到"写的；
> 对一个不存在的文章 id 这么说，用户只会以为是页面坏了。所以另写了
> `not_found_page()`。

#### 问题 ②：浏览计数不能和详情查询放进同一个事务

直觉上"查询 + 计数自增"应该原子。但这个页面的访问特征决定了相反的选择：

**详情页是人人都会访问的页面。把它变成写热点，代价远大于少记几次浏览量。**

**解决：** 计数单独一条 `UPDATE`，**故意不包进事务**，理由是"包成一个事务只会拉长
持锁时间"。并且计数失败**不让页面挂掉**：

```cpp
if (!db_exec("UPDATE article SET view_count = view_count + 1 ..."))
    LOG_WARN("article_detail: view_count update failed, id=%lld", aid);  // 记日志继续渲染
else
    ++views;
```

注意 `LOG_WARN` 而不是 `LOG_ERROR`，并且 `else` 分支才 `++views`——**渲染的数字
和库里的数字保持一致**，不会出现"页面显示 5、库里是 4"。

#### 问题 ③：乱码——连接池没设字符集

中文内容乱码，而且**时好时坏**。全英文内容永远正常。

**根因：** `sql_connection_pool.cpp` 只调了 `mysql_init` + `mysql_real_connect`，
**没有 `mysql_set_character_set`**。库是 utf8mb4，但连接用的是客户端库的默认值。
"时好时坏"是因为连接池里每条连接的字符集状态取决于它建立时的配置，
表现随"你抽到哪条连接"而变。

**解决：** 建连接时显式 `mysql_set_character_set("utf8mb4")`。

> 字符集问题最典型的特征就是"只在非 ASCII 上出现，且看起来是随机的"。这也再次
> 说明了 2.1 问题 ③ 为什么必须在边界测试里专门造**中文**的长度用例。

**一句话讲法：** "详情页有两个设计决定可以讲：一是浏览计数**故意不放在同一个事务
里**——详情页是热点读页面，包进事务只会拉长持锁时间，少记几次浏览量比锁冲突
划算；二是计数失败不阻断渲染，但记 `LOG_WARN` 且只在成功时才加一，保证页面
显示的数字和库里的数字一致。"

### 2.7 发评论

**做了什么：** `POST /api/comment/create`，参数 `article_id` / `content`，
302 回详情页。

**关键实现：** `http/http_conn.cpp:1520` `handle_comment_create()`

#### 问题 ①：外键的报错对用户毫无意义

`comment.article_id` 有外键指向 `article`。对一篇不存在的文章发评论，外键会拦下来
（错误码 1452）。但这个报错：

- 对用户毫无意义（他看到的是一句 MySQL 的英文错误）
- 会把**一次正常的用户输入错误**变成一行 `LOG_ERROR`，污染错误日志

**解决：** 插入前**主动查一次**文章是否存在，给 404 + "要评论的文章不存在或已被
删除"。**外键留在那里当兜底，但不再是第一道防线。**

> 这和 2.1 的 1062 是**相反**的取舍，值得对比着讲：重名交给数据库唯一键（因为
> 那是"并发正确性"问题，只有数据库能原子判断），而"文章不存在"应用层先查
> （因为那是"用户提示"问题，数据库能做但给出的信息没用）。**同一个人做的两个
> 相反决定，判断依据是"这个约束解决的是正确性问题还是体验问题"。**

#### 问题 ②：评论长度上限的连锁约束

`comment.content` 是 `VARCHAR(1000)` → 服务端 `COMMENT_MAX = 1000`（按字节）→
但 HTML 表单上写的是 `maxlength="330"`。

**为什么 330 而不是 1000：** `maxlength` 数的是**字符**，而 1000 是**字节**。
一个中文 3 字节，`1000 / 3 ≈ 333`，取 330 留一点余量。**前端的字符计数和后端的
字节计数必须换算，否则中文用户会被前端的 `maxlength` 放行、被后端的 400 拦下。**

**一句话讲法：** "评论功能里有个值得对比的取舍：对'文章不存在'，我**没有**靠外键
的 1452 兜底，而是插入前主动查一次——因为外键能保证正确性，但它给出的报错对
用户毫无意义，还会把一次正常的输入错误变成错误日志。反过来，注册的重名判断
我**交给**了数据库的 1062。区别在于前者是体验问题、后者是并发正确性问题。"

### 2.8 关注

**做了什么：** `POST /api/follow`，参数 `followee_id`，成功后跳转到对方主页。

**关键实现：** `http/http_conn.cpp:1580` `handle_follow()`

#### 问题 ①：联合主键拦不住"关注自己" ⭐

`follow` 表的主键是 `(follower_id, followee_id)`。直觉上它保证"同一对不重复"，
那么自己关注自己 `(5, 5)` 呢？

**实测确认：完全放行。** 联合主键只保证**组合唯一**，`follower_id == followee_id`
是合法的行。

**解决：** 应用层显式拦：

```cpp
if (target == m_user_id) return ...("不能关注自己。");
```

> 这个坑的教训是"**别把约束的语义想当然**"。主键约束的是唯一性，不是合理性。
> 我是在阶段 1 实测才确认它真的放行的——如果没测，这会变成一个数据里真实存在
> 的畸形行，而且粉丝数会把自己算进去。

#### 问题 ②：连点两下"关注"不能报错

**解决：** `INSERT IGNORE`——重复关注不报 1062，直接当成功。**幂等是必须的**，
用户连点两下不该看到报错。取关同理，用 `DELETE`，影响 0 行也算成功。

#### 问题 ③：复合主键的最左前缀，让"查粉丝"全表扫

`follow` 主键 `(follower_id, followee_id)` 的最左前缀是 `follower_id`，所以：

| 查询 | 走索引吗 |
|---|---|
| "我关注了谁" → `WHERE follower_id = ?` | ✅ 走主键前缀 |
| **"谁关注了我"（查粉丝）** → `WHERE followee_id = ?` | ❌ **用不上主键，全表扫** |

**解决：** 额外补一个 `KEY(followee_id)`。

**这是复合主键的经典陷阱**：建表时按"哪个字段更像主键"来排序，而不是按**查询
模式**来排。正确做法是先想清楚"这张表会被怎么查"，再决定列序。

**一句话讲法：** "关注功能里有两个坑。一是 `(follower_id, followee_id)` 这个联合
主键**不拦自己关注自己**——主键约束的是组合唯一，不是关系合理性，我是实测才确认
的，现在在应用层显式拦。二是最左前缀：查粉丝走 `followee_id` 用不上主键，必须
额外补索引，这就是'按查询模式定列序'而不是'按哪个字段像主键定列序'。"

### 2.9 关注流

**做了什么：** `GET /api/feed?page=N`，展示"我关注的人"发的文章；页面顶部同时
显示我的关注数/粉丝数/文章数。

**关键实现：** `http/http_conn.cpp:1661` `handle_feed()`

#### 问题 ①：`ORDER BY` 跨 JOIN 会建临时表再排序

```sql
SELECT a.article_id, a.title, a.create_time, u.username
FROM follow f
JOIN article a ON a.user_id = f.followee_id
JOIN user    u ON u.user_id = a.user_id
WHERE f.follower_id = ?
ORDER BY a.create_time DESC, a.article_id DESC
LIMIT 20 OFFSET ?
```

`EXPLAIN` 显示 JOIN 确实走了索引（`f` 走主键最左前缀、`a` 走 `idx_user_time`），
但 `Extra` 里有 **`Using temporary; Using filesort`**——**`ORDER BY` 跨 JOIN 需要
先建临时表再排序，这才是数据量上来之后的瓶颈。**

**当前的诚实状态：** 数据量小（`follow` 只有几行）时根本看不出来。**这是关系模型
的固有代价，不是 bug**，属于已知不足、尚未优化。

> 相关的一个方法论坑：**28 行的小表上 `EXPLAIN` 会骗人**——优化器明确选择了
> `type=ALL` + `Using filesort`，即使索引存在，因为小表上全表扫确实更便宜。
> **不能拿小表上的 `EXPLAIN` 判断索引设计对不对**，要灌到真实数据量（当时灌了
> 5 万篇）再看。

#### 问题 ②：三个 `COUNT(*)` 现在够用，但那是有条件的

顶部三个计数（粉丝/关注/文章）各是一次 `COUNT(*)`，都有索引支撑
（`idx_followee`、follow 主键前缀、`idx_user_time`），当前数据量下够用。

**为什么不现在就优化成冗余计数列：**"真上量了再考虑冗余计数列 + 事务维护——
现在别过早优化。" 冗余计数列会把每个关注/取关操作变成"写 follow 表 + 更新计数
列"的两步，必须包在事务里，**复杂度是立刻要付的，收益是将来才有的**。

**一句话讲法：** "关注流的实话是：`ORDER BY` 跨 JOIN 会产生
`Using temporary; Using filesort`，`EXPLAIN` 里看得很清楚。当前数据量下不体现，
数据量上来后这是第一个瓶颈。我把它**如实留在记录里没有改**——因为它需要的是
反范式设计（比如在 article 上冗余 author 信息，或者用覆盖索引把排序搬回单表），
是个有明确取舍的改动，不该在没有真实数据量的情况下拍脑袋做。"

### 2.10 个人主页

**做了什么：** `GET /api/profile?id=N`，展示用户名、加入时间、文章数/粉丝数/关注数，
以及关注/取关按钮。**不传 `id` 就是看自己**。

**关键实现：** `http/http_conn.cpp:1772` `handle_profile()`

#### 问题 ①：未登录且不带 `id` 时没有可展示的内容

```cpp
long long target = to_ll(get_param("id"), -1);
if (target <= 0) target = m_user_id;      // 不传 id 就看自己
if (target <= 0) return require_login();  // 未登录又没有 id，没有可展示的主页
```

**解决：** 两级回落——先回落到"自己"，如果连自己都没有（未登录），才要求登录。
**顺序不能反**，否则登录用户访问 `/api/profile` 也会被要求登录。

#### 问题 ②：按钮该显示"关注"还是"取关"

**解决：** 登录且不是自己时，多查一次"我是否已关注 TA"（`SELECT 1 FROM follow
WHERE follower_id = ? AND followee_id = ? LIMIT 1`），决定渲染哪个按钮。

**为什么这个额外查询是值得的：** 它是这个页面上唯一的**个性化**查询，代价是
一次走主键前缀的点查；没有它，用户只能靠"点了关注会不会报错"来判断当前状态。

**一句话讲法：** "个人主页是个'组装页'：它把四张表的信息拼在一起——用户基本信息、
三个计数、以及'我是否已关注 TA'。这里有个小小的设计点是 `id` 的两级回落：
先回落到自己，再回落到要求登录，顺序反了的话登录用户也会被拦。"

## 3. 横切关注点：每个 handler 都要遵守的铁律

这三个功能之外，有三条规则是**所有**业务代码共同遵守的，写在业务区分节的注释里
（`http/http_conn.cpp:1187`）：

```
1. user_id 一律取自 session（m_user_id），绝不从请求参数里读。
2. 字符串参数一律 sql_escape 后再拼进 SQL；数字参数一律 to_ll 转整数。
3. 渲染进 HTML 的用户内容一律 html_escape，否则是存储型 XSS。
```

### 3.1 为什么是"输出时转义"而不是"输入时转义"

**同一份数据可能有多种输出上下文**（HTML、JSON、URL）。在输入时转义会让"这份数据
到底被转过几次"变得不可知，很容易变成双重转义（用户看到一个真实的 `&#39;`
显示成了 `&amp;#39;`）。

**前端的转义也不行**：接口是公开的，攻击者可以直接 POST 绕过前端；而且前端转义
防的是"渲染时"的 XSS，防不住**存储型** XSS 的入库。

**一个具体的细节：** `html_util.cpp` 里单引号转义成 `&#39;`，**不是
`&apos;`**——后者在 HTML4 里是未定义的实体。

> 这个细节在写冒烟测试时反过来帮了我：我断言"注入载荷原样出现在页面上"失败，
> 排查后发现单引号被转义成了 `&#39;`——**这条失败恰恰证明转义是对的**。改成
> 断言转义后的实体形态之后，反而成了更强的检查。

### 3.2 CSRF：`Origin` 与 `Host` 比对，以及那个只在写请求上出现的陷阱

写接口锁 POST 挡不住 CSRF（跨站表单一样能 POST）。防护做成：比对 `Origin` 和
`Host`，**忽略 scheme、但保留端口**。

**这里有个非常隐蔽的坑：** 反向代理如果写 `proxy_set_header Host $host;`
而不是 `$http_host`，**端口会被丢掉**：

| | 浏览器发出的 | 后端解析出的 authority | 结果 |
|---|---|---|---|
| `Origin` | `https://127.0.0.1:8443` | `127.0.0.1:8443` | —— |
| `Host` 用 `$http_host` | `127.0.0.1:8443` | `127.0.0.1:8443` | **相等，放行** |
| `Host` 用 `$host` | `127.0.0.1` | `127.0.0.1` | **不等，403** |

失效方式是"**每个写请求都被自己人拒掉，而读请求完全正常**"，看上去非常像
"CSRF 防护太严了"，排查方向很容易被带偏。

**这条是实测的，不是推演**：把同一份配置的 `$http_host` 换成 `$host`，
`POST /api/article/create` 从 302 变成 403，而同端口的 `GET /judge.html` 仍是 200。

### 3.3 未认证的远程 DoS：一个 `Content-Length: -1` 打崩整个服务 ⭐

**现象：** 一个 `Content-Length: -1` 的请求就让服务进程崩溃（端口不再监听）。

**根因：** `atol` 解析出 `-1`，一路流到 `parse_form(text, (size_t)(-1))`，
**负数被转成 `SIZE_MAX`**，解析循环越界读到段错误。

**影响放大：** 这是**单进程**架构，所以一条请求就能让所有用户的服务中断，
**而且不需要任何认证**。

**解决：** 两处。解析层不用 `atol`/`strtoll` 裸收（它们会把 `-1`、`12abc` 这类
都收下），改用能报告失败的转换；`parse_content` 入口再挡一道：

```cpp
if (m_content_length < 0 || m_content_length > MAX_CONTENT_LENGTH) → 400
```

**讲法：** "输入校验要发生在**类型转换处**，而不是等它变成合法类型之后再判断。
`-1` 变成 `SIZE_MAX` 是 C++ 里'有符号转无符号'的经典陷阱。"

### 3.4 日志脱敏：留结构不留值

原来 `add_response` 把整个响应头写进日志、`process_read` 把 POST 正文写进日志，
于是**明文口令和 session_id 都会落盘**。

**解决：** 按"**留结构不留值**"的原则脱敏——请求行的查询串记成
`GET /api/login?user=?&password=?`，Cookie 记成 `<redacted>`，请求正文记成
`<requests body: N bytes>`。

**为什么不用"敏感参数名单"：** 名单漏一个等于没做，而且**新增参数默认会被记
下来**，方向是错的。按结构脱敏是白名单式的，默认安全。

实测：新增日志行的凭据泄漏数为 0（明文口令、salt、hash、会话 ID、Set-Cookie
全部 0 命中），同时日志里的语句结构仍足够定位问题。

### 3.5 一个我自己造的坑：台账成了泄漏源

写"凭据不该进版本库"的记录时，正文里把原始代码那三行**连同一个真实口令一起照抄
了进去**。结果这份讲脱敏的文档自己成了泄漏源，进了 3 个 commit。

**发现方式：提交前的全树扫描**（而不是靠"我记得我脱敏了"）。
**修法：** 值换成占位符 + 重写 git 历史（尚未推送，代价为零）。

**教训：脱敏规则要作用于全部文本，包括"讲脱敏"的那段文字本身；凡是要复述敏感值
的场合一律用占位符。别信自己的记忆，提交前扫一遍。**

## 5. 追问速查

**Q：这批功能里你觉得最有技术含量的是哪个？**
列表页的分页（2.5 ②）和发帖的长度上限推导（2.4 ②）。前者是因为它**只在真实
数据量和并发下才暴露**，而且修法恰好和 InnoDB 二级索引的物理结构对上了；后者
是因为它是两个独立约束**互相打架**，需要反推才能定下来。

**Q：为什么不做成前后端分离 / 返回 JSON？**
原项目的响应机制是"拼字符串 + `writev`"，加一层 JSON 序列化和前端渲染框架会
把改动面放大到整个前端，而收益在这个项目里几乎为零（没有复杂交互、没有多端
复用需求）。**服务端渲染是这里的合理选择，不是能力不足。**

**Q：如果让你重做，会怎么改？**
三点：① 测试应该进 CI 而不是放 `/tmp`；
② 凭据/日志级别这类东西应该在**第一次提交前**就确定；③ 压测要在同一台干净的
机器上、固定环境做，并先记录 `MemAvailable` 和 swap 使用量。

**Q：你说"补了地基"，那地基里最难的是哪块？**
会话（`session/session_manager`，286 行）。因为它要求的不是"写一个哈希表"，而是
想清楚三件事：TTL 和容量上限怎么配合、超限淘汰怎么保证无歧义（2.3 ② 的单调
序号）、以及换账号登录时旧会话的语义。这三条里任何一条想错，表现都是"偶发地
掉登录态"——**最难查的那类 bug**。
