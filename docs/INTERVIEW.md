## 0. 先看这个：三个时长的讲法

面试官给你的时间通常是 30 秒、2 分钟或 5 分钟。先把三套话术背熟，细节留到提问环节再展开。

### 30 秒版

> 我在一个开源的 C++ Web 服务器（TinyWebServer，epoll + 线程池 + 定时器 + MySQL
> 连接池）上，从零加了一套论坛业务：用户、文章、评论、关注四张表，12 个接口，
> 服务端直接渲染 HTML。因为原项目没有会话、没有参数解析、也没有真正的动态响应，
> 所以我先补了一层地基，再写的业务。过程中修掉了几个真实缺陷，比如一个
> `Content-Length: -1` 的请求就能把整个单进程服务打崩。

### 2 分钟版

在上面基础上加三件事：

1. **增量边界要主动说**：原项目是开源的，我做的不是"写了一个 Web 服务器"，而是"在它上面加了一个业务模块，并补掉了它支撑这个业务所缺的公共层"。这句话不说清，面试官一旦追问底层实现（epoll 怎么用、线程池怎么调度），你会很被动。
2. **地基比业务难**：真正的成本在阶段 0，不在写接口。原项目里 `cgi` 只是个"是不是 POST"的标志位、表单解析写死了 `"user="` 的 5 字节偏移、动态响应体超过 1024 字节会**静默失败**。这些不先解决，业务接口根本写不下去。
3. **有实测数据也有实测教训**：写了一个 52 项断言的冒烟脚本，覆盖全链路加六类负向用例；更早的版本还跑过 316 项断言的 ASan 全量复验（0 份报告）。同时我把一个没查清的性能问题原样留在了记录里，没有拿"调了编译选项"糊过去。

### 5 分钟版

在 2 分钟版之后，讲清这四块（每块 40 秒左右）：

- **数据模型**：四张表，覆盖 1:n（用户→文章、用户→评论、文章→评论）和 n:n 自关联（用户↔用户关注）。
- **两个安全设计**：服务端会话（`HttpOnly` + `SameSite=Lax`）与 CSRF 的 `Origin`/`Host` 比对。
- **口令存储**：从明文迁到 bcrypt，且是**登录时渐进迁移**，不需要停服。
- **一个具体的故事**：挑第 7 节里任何一个坑讲。建议讲"悬空指针"或"未认证 DoS"，这两个既有技术深度，又能体现排查方法。

## 2. 基线诊断：动手前的 6 个事实

这六条是我读原代码后、动手写业务之前先确认的。它们决定了"为什么必须有个阶段 0"。

| 事实 | 位置 | 对加论坛的影响 |
|---|---|---|
| **没有真正的 CGI**，`cgi` 只是"是不是 POST"的标志位 | `http/http_conn.cpp` 路由分发处 | 路由靠 URL 末段首字符硬编码分发，字符空间不够 |
| **路由约定 0/1/2/3/5/6/7 各占一个字符** | 同上 | 要加十来个接口，一个字符的地址空间不够用 |
| **表单解析写死了 `"user="` 的 5 字节 / `"&password="` 的 10 字节偏移** | 同上 | 完全无法复用，必须重写 |
| **动态响应体只能走 `add_content()`，超过 1024 字节静默失败** | `http/http_conn.h:42` 的 `WRITE_BUFFER_SIZE` | 表现为"连接莫名断开"，没有任何报错 |
| **连接池建连接时没设字符集** | `CGImysql/sql_connection_pool.cpp` | 中文会乱码，而且时好时坏（全英文内容永远正常） |
| **线程池在调 `process()` 之前已经取好一条连接** | `threadpool/threadpool.h`（`connectionRAII`） | 业务代码里**不能**再取第二条，池子只有 8 条 |

第 6 条是最容易踩的：它意味着事务不能像教科书那样"自己再拿一条连接"，否则要么占满池子，要么事务跨了两条连接而**静默失效**。

## 3. 数据模型

四张表，`db/schema.sql`：

```
user ──1:n──> article ──1:n──> comment
  │              │              ▲
  │              └──────────────┘
  └──n:n（自关联）──> follow
```

设计上值得一提的三点：

1. **`user` 表是迁移而不是新建**。原表已经有数据，所以是 `ALTER` 补主键与唯一键，存量账号直接沿用——不能因为要加业务就把老用户丢掉。
2. **`follow` 表的主键是 `(follower_id, followee_id)`**。主键的最左前缀是 `follower_id`，所以"我关注了谁"走主键没问题，但**"谁关注了我"（查粉丝）用不上主键**，必须额外补一个 `KEY(followee_id)`，否则全表扫。这是复合主键的经典陷阱。
3. **五条外键统一 `NO ACTION`，不做级联删除**。一次误删 `user` 会顺着带走他所有的帖子和评论，而这个代价不可逆。代价是清理测试数据必须按 `comment → article → follow → user` 的顺序删——**直接删 `user` 会被外键挡下来**，这一点我第一次写清理脚本时就想当然了。

## 4. 接口清单

12 个接口，路由表在 `http/http_conn.cpp:934` 的 `route_table()`：

| 接口 | 方法 | 需要登录 | 说明 |
|---|---|---|---|
| `/api/register` | POST | 否 | 注册，成功后直接建会话 |
| `/api/login` | POST | 否 | 登录 |
| `/api/logout` | POST | 否 | 登出，服务端销毁会话 |
| `/api/whoami` | GET | 否 | 返回当前用户 id，未登录返回 `not logged in` |
| `/api/article/create` | POST | **是** | 发帖 |
| `/api/article/list` | GET | 否 | 文章列表，分页 |
| `/api/article/detail` | GET | 否 | 文章详情 + 评论列表 |
| `/api/comment/create` | POST | **是** | 发评论 |
| `/api/follow` | POST | **是** | 关注（跳转到对方主页） |
| `/api/unfollow` | POST | **是** | 取关 |
| `/api/feed` | GET | **是** | 关注流（我关注的人的文章） |
| `/api/profile` | GET | 否 | 个人主页：文章数 / 粉丝数 / 关注数 |

外加两个**保留的旧别名**：`/3CGISQL.cgi`（注册）、`/2CGISQL.cgi`（登录）。它们只是路由表里两行——存量页面和用户书签指向的是这两个路径，删掉等于把这些入口变成 404，保留的成本几乎为零。

路由表把"**是否只接受 POST**"也变成了数据的一部分（`Route{handler, post_only}`），而不是散落在各个 handler 里的 `if`。写接口收到 GET 返回 405 + `Allow: POST`；合法但未实现的方法（PUT/DELETE 等）返回 501 + `Allow: GET, POST`——这两个码的区别是 RFC 语义，不是随便挑的。

## 6. 值得单独拿出来讲的 5 个设计决策

### 6.1 为什么把 TLS 放在 nginx 而不是做进 C++ 服务

服务里每一个字节的收发只经过**四个 socket 调用点**（LT/ET 两处 `recv`、`close_conn` 里排空输入的 `recv`、`write` 里的 `writev`）。要支持 TLS 就得把这四个全换成 `SSL_read`/`SSL_write`，再加上非阻塞握手状态机、`SSL_ERROR_WANT_READ/WANT_WRITE` 的重试语义，以及"`writev` 在 TLS 里没有对应物"这个必须手写分段发送的问题。

这些改动**全部落在每个请求都要走的热路径上**，而它带来的收益（证书轮换、TLS 版本策略、HSTS、OCSP stapling、HTTP/2）代理已经全给了。所以选择代理终止 TLS。

配套的一个决定：**后端默认只监听 `127.0.0.1`**。这不是保守——如果绑到 `0.0.0.0`，同网段任何人都能 `http://内网IP:9006` 直连后端，绕过 TLS 和代理上的所有策略；更糟的是这条路**不需要攻击者做任何事**就能拿到已登录用户的响应，因为 Cookie 带了 `SameSite=Lax; HttpOnly` 但**没有 `Secure`**，浏览器在明文 `http://` 请求上照样会带上它。

### 6.2 CSRF 为什么比对 `Origin` 和 `Host`，以及那个"只在写请求上出现"的陷阱

写接口锁了 POST 并不能防 CSRF——跨站表单一样可以 POST。防护做成：`Origin` 与 `Host` 比对，**忽略 scheme、但保留端口**。

这里有个非常隐蔽的坑：反向代理如果写 `proxy_set_header Host $host;`（而不是 `$http_host`），端口会被丢掉。

| | 浏览器发出的 | 后端解析出的 authority |
|---|---|---|
| `Origin` | `https://127.0.0.1:8443` | `127.0.0.1:8443` |
| `Host` 用 `$http_host` | `127.0.0.1:8443` | `127.0.0.1:8443` → **相等，放行** |
| `Host` 用 `$host` | `127.0.0.1` | `127.0.0.1` → **不等，403** |

失效方式是"**每个写请求都被自己人拒掉，而读请求完全正常**"，看上去非常像"CSRF 防护太严了"，排查方向很容易被带偏。这条是实测过的，不是推演：把同一份配置的 `$http_host` 换成 `$host`，`POST /api/article/create` 从 302 变成 403，同端口的 `GET /judge.html` 仍是 200。

### 6.3 口令为什么用 bcrypt，以及"渐进迁移"

原项目明文存口令。迁移到 bcrypt（cost 10）时面临一个现实问题：库里已经有存量账号，怎么做迁移？

做法是**登录时迁移**：登录请求先按老路径校验明文，通过后立刻把 bcrypt 散列写回，并清空明文列。老账号第一次登录即完成迁移，用户无感，不需要停机，也不需要写一次性迁移脚本。

存储格式是自描述的（`$2b$10$` + 22 字符 salt + 31 字符散列），所以算法标识、cost、salt 都在串里，将来调 cost 不需要改表结构。

另外补了两个边界：`hash("")` 与 `verify("", h)` 的语义统一为"拒绝"（空口令从来不是合法凭据），以及长度上限在跑 bcrypt **之前**就挡掉——bcrypt cost 10 单次约几十毫秒，用超长用户名去跑完整散列是白送的算力消耗，而 `username` 列宽只有 64，超了在库里必然不存在。

### 6.4 会话过期为什么需要一个单调序号

会话有 `TTL`（24 小时）加上限（10 万条），超限时淘汰"最久未活动"的一条。第一版直接用 `time()` 给 `last_active` 打时间戳，问题是 **`time()` 只有秒级精度**：同一秒内建立的所有会话 `last_active` 完全相同，"最久未活动"就退化成哈希表的遍历顺序。

这不是理论问题——表被撑满恰恰发生在**登录突发**的时候，而登录突发就是同一秒内建一堆会话。修法是加一个单调递增的序号做无歧义的 tiebreaker。

### 6.5 注册的"重名判断"为什么改成捕获 1062

原做法是"先查再插"。`user` 表加了唯一键之后，正确做法是**直接 INSERT，捕获 1062（重复键）错误**：把"先查后插"之间的竞态窗口整个消掉，而且比在内存里维护一份用户名 map 更可靠。判断重名交给数据库的唯一约束，那是它本来就该干的活。

## 7. 踩过的坑（按面试杀伤力排序）

每条的讲法都是：**现象 → 根因 → 怎么定位 → 怎么修**。这是整份文档最有价值的部分，建议至少熟记前四条。

### 7.1 悬空指针：`std::vector` 扩容把三个裸指针变成了悬空指针 ⭐

- **现象**：`Content-Length` 大到一定程度时请求返回 400；更早的现象是"某些请求莫名其妙走错路由"。
- **根因**：`m_read_buf` 是 `std::vector<char>`，`grow_read_buf()` 里的 `resize()` **会重新分配**，而 `m_url` / `m_host` / `m_version` 当时是**指向它的裸指针**——扩容后全部悬空。`do_request()` 恰恰是在扩容**之后**才拿 `m_url` 去查路由表，于是拿着一个可能已被释放/搬移的地址去比较。
- **怎么定位**：不是一眼看出来的。先把 400 的触发条件缩到最小（内容长度分档：1900 和 5000 返回 400，其余 200），再顺着"谁在扩容之后读了这个指针"一路查过去。
- **修法**：让解析结果不再指向会重分配的缓冲——把三个成员改成 `std::string`（拷贝）。`http/http_conn.h:208` 那里留了注释说明为什么不能用指针。
- **面试怎么讲**：这是一个"**生命周期管理**"的典型题。可以延伸到：为什么 `string_view`/裸指针在这个场景不适用、什么情况下可以选择"先 reserve 到足够大再解析"（把扩容风险前移到解析之前），以及为什么在 C++ 里让成员持有 `std::string` 通常比持有指针+手工同步更划算。

### 7.2 未认证的远程 DoS：一个 `Content-Length: -1` 就打崩整个服务 ⭐

- **现象**：一个 `Content-Length: -1` 的请求就让服务进程崩溃（端口不再监听）。
- **根因**：`atol` 解析出 `-1`，一路流到 `parse_form(text, (size_t)(-1))`，负数被转成 `SIZE_MAX`，解析循环越界读到段错误。
- **影响放大**：这是**单进程**架构，所以一条请求就能让所有用户的服务中断，而且不需要任何认证。
- **修法**：两处。解析层不用 `atol`/`strtoll` 裸收（它们会把 `-1`、`12abc` 这类都收下），改用能报告失败的转换；`parse_content` 入口再挡一道 `m_content_length < 0 || > MAX_CONTENT_LENGTH`（`http/http_conn.cpp:719`）。
- **面试怎么讲**：这题能体现"**输入校验要发生在类型转换处，而不是等它变成合法类型之后再判断**"。`-1` 变成 `SIZE_MAX` 是 C++ 里"有符号转无符号"的经典陷阱；延伸可以聊 `std::from_chars`、以及为什么"边界值要么在解析时拒绝，要么在解析时饱和"。

### 7.3 启动期的错误被推迟到运行期才崩 ⭐

- **现象**：`WebServer::log_write()` 丢掉了 `Log::init()` 的返回值。当日志文件打不开时（目录只读、磁盘满）`m_fp` 为 `NULL`，之后**第一个处理请求的线程**在 `fputs(..., NULL)` 上把整个服务打崩。
- **为什么恶劣**：崩在现场是业务代码（`fputs`），根因却在启动时（没检查 init 的返回值）。排查的人会一头扎进业务逻辑里。而且它在启动时"看起来是成功的"——进程活着、端口也在监听。
- **修法**：检查返回值，启动失败就明确退出，而不是带着 `NULL` 文件指针继续跑。
- **面试怎么讲**：这是"**fail fast**"原则的具体案例：初始化阶段的失败必须在初始化阶段暴露。可以延伸到 RAII 资源包装、以及为什么"构造函数里不做可能失败的事"和"初始化函数必须返回状态"是同一件事的两面。

### 7.4 `add_content()` 超过 1024 字节静默失败

- **现象**：动态页面稍微长一点，**连接就被直接关掉**，没有任何日志、没有任何错误码。
- **根因**：`add_response()` 放不下就返回 `false`，一路传到 `process_write` 返回 `false`，然后连接被关。`WRITE_BUFFER_SIZE` 是 1024（`http/http_conn.h:42`）。
- **修法**：动态内容一律挂到 `m_iv[1]` 上（`http/http_conn.h:157` 有注释），不再走那个 1024 字节的写缓冲。
- **面试怎么讲**："**静默失败是比报错更糟的失败**"。这个 bug 的表现（连接断开）和根因（写缓冲太小）之间隔了三层，是"错误处理缺失"的典型案例。

### 7.5 连接池没设字符集 → 中文时好时坏地乱码

- **现象**：中文内容乱码，而且**时好时坏**。
- **根因**：`sql_connection_pool.cpp` 只调了 `mysql_init` + `mysql_real_connect`，没有 `mysql_set_character_set`。库是 utf8mb4，但连接用的是客户端库默认值。
- **为什么"时好时坏"**：**全英文内容永远正常**，只有中文才暴露；而且连接池里每条连接的字符集状态依赖它被建立时的配置，所以表现会随"你抽到哪条连接"而变。
- **修法**：建连接时显式 `mysql_set_character_set("utf8mb4")`。
- **面试怎么讲**：字符集问题最典型的特征就是"只在非 ASCII 上出现，且看起来是随机的"。这也解释了为什么边界测试要专门造**中文**的长度用例（`username` 是 `VARCHAR(64)`，中文一个字占 3 字节，85 个中文字就超了——**按字符数校验根本拦不住，必须按字节算**）。

### 7.6 复合主键的最左前缀

`follow` 表主键 `(follower_id, followee_id)` 的最左前缀是 `follower_id`，所以"查我的粉丝"（按 `followee_id` 查）**用不上主键**，必须补 `KEY(followee_id)`，否则全表扫。这是复合主键的经典陷阱：建表时按"哪个字段更像主键"来排序，而不是按**查询模式**来排。

### 7.7 `LOG_*` 宏内部的 `if` 吃掉了 `else`

- **现象**：带 `else` 的 `if` 语句行为诡异（编译能过，逻辑不对）。
- **根因**：`LOG_*` 宏展开成 `if (0 == m_close_log) { ... }`，用的时候写成 `if (cond) LOG_DEBUG(...); else ...`，宏内部的 `if` 把 `else` 抢走了。
- **修法**：宏内层加花括号。这个坑我踩了**两次**——第二次说明"记住教训"和"形成习惯"是两件事。

### 7.8 误删用户：备份是在"订正数据"之后才做的话就白做了

- **现象**：清理测试用户时用"删掉不在备份里的行"作为条件，结果**误删了一个真实账号**。
- **根因**：备份是在订正一条 URL 编码用户名**之前**做的。那个用户名在备份里是 `%E9%91%AB%E5%93%A5`，订正成中文后，它当然"不在备份里"，于是被当成测试数据删掉。
- **修法**：按原值恢复用户，验证三个原始账号都能正常登录。
- **教训**：**备份必须紧贴删除动作之前做**，中间不能夹任何数据修改。这之后所有清库操作都先快照再比对。

### 7.9 压测脚本把"残留的旧进程"当成了"启动成功"

- **现象**：四轮"不同配置"的压测结果几乎一样。
- **根因**：`-O2` 那一轮的 OLD 二进制**根本没起来**（端口占用导致 bind 失败退出）。而脚本检查"端口是否在监听"来判断启动成功——端口确实在监听，只不过是被**上一轮残留的 NEW 进程**占着的。于是四轮压的都是同一个进程。
- **修法**：停止逻辑改成**按端口找持有者 PID**，启动后还要 `readlink /proc/<pid>/exe` 确认跑的是刚启动的那个二进制。
- **面试怎么讲**：这是"**实验方法论**"的题，比技术细节更稀缺。可以讲：一个和上次矛盾的结果，应该先怀疑测量工具而不是被测对象；"进程还活着"不等价于"你启动的那个进程还活着"。

### 7.10 `pkill -f` 把执行它的 shell 自己杀了（exit 144）

- **现象**：执行 `pkill -f <pattern>` 的 shell 自己被杀死，退出码 144，整轮工作丢失。
- **根因**：`pkill -f` 匹配的是**完整命令行**，而调用它的 shell 的命令行里就包含那个 pattern。这个坑同样踩了**两次**。
- **另一个变体**：`pkill -x <name>` 匹配的是 `comm`（进程名）而不是路径，压测脚本会把二进制复制成不同文件名，于是 `comm` 变了，`pkill -x server` 什么都匹配不到，旧实例存活、端口被占——正好就是 7.9 那个事故的成因。
- **修法**：按端口持有者 PID 杀，杀完确认。**永远不要写一个能匹配到自己命令行的 pattern。**

### 7.11 `make` 不跟踪编译标志

- **现象**：`make server DEBUG=0` 什么都不做，拿到的还是旧的 `-g` 二进制。
- **根因**：`make` 判断目标是否需要重建只看依赖文件的时间戳，**不看命令行变量**。目标已存在且比依赖新，就判定 up to date。
- **修法**：`make clean && make server DEBUG=0`。
- **顺带**：这条是因为我把它写进了自己的笔记，后来复查时发现笔记本身是错的才揪出来的——**记录错了比没记录更危险**。

### 7.12 日志脱敏：请求行、Cookie、请求正文

- **问题**：原来 `add_response` 把整个响应头写进日志、`process_read` 把 POST 正文写进日志，于是**明文口令和 session_id 都会落盘**。
- **修法**：按"**留结构不留值**"的原则脱敏——请求行里的查询串记成 `GET /api/login?user=?&password=?`，Cookie 记成 `<redacted>`，请求正文记成 `<requests body: N bytes>`。
- **为什么不用"敏感参数名单"**：名单漏一个等于没做，而且**新增参数默认会被记下来**，方向是错的。按结构脱敏是白名单式的，默认安全。
- 实测：新增日志行的凭据泄漏数为 0（明文口令、salt、hash、会话 ID、Set-Cookie 全部 0 命中），同时日志里语句结构仍足够定位问题。

### 7.13 台账自己成了泄漏源（这一条是最近才发生的）

我写了一份"凭据不该进版本库"的记录，正文里却把原始代码那三行**连同一个真实口令一起照抄了进去**。结果这份讲脱敏的文档自己成了泄漏源。

发现方式是**提交前的全树扫描**（而不是靠"我记得我脱敏了"），修法是把值换成占位符并重写 git 历史（尚未推送，代价为零）。

教训：**脱敏规则要作用于全部文本，包括"讲脱敏"的那段文字本身**；凡是要复述敏感值的场合一律用占位符，不要图省事抄原文。以及——**别信自己的记忆，提交前扫一遍**。

### 7.14 测试脚本的期望值写错，和"永远会通过的假断言"

冒烟脚本第一次跑出 5 个失败，其中**全部**是脚本自己的期望写错，不是被测代码的问题：

- 我按发帖的 302 想当然，以为注册/登出也返回 302，实际服务端返回 **200 并渲染页面**（`serve_file`）。只有改数据的业务接口才走 302 + `Location`。
- 断言"注入载荷原样出现在页面上"失败，因为单引号被转义成了 `&#39;`——**这条失败恰恰证明转义是对的**。改成断言转义后的实体形态，反而成了更强的检查。
- 我还写过一条 `check(..., c.cookie == x or True)` ——`or True` 让它**永远通过**。这种假断言比没有断言更糟，因为它会给你虚假的信心。

另外有两个"边界用例"其实是脚本自己坏了：声明 `Content-Length: 49152` 却不发送正文（服务端在等正文）；`curl -o /dev/null` 只作用于命令行里的第一个 URL，后面的响应体漏到了 stdout 上，把断言自己的输出骗了。

**这些的共性**：失败出现时，第一件事是判断"是代码错了还是我的期望错了"，而不是直接去改代码。

### 7.15 小表上的 `EXPLAIN` 会骗人

28 行的小表上，优化器明确选择了 `type=ALL` + `Using filesort`，即使索引存在。**小表上全表扫确实更便宜**，所以不能拿小表上的 `EXPLAIN` 判断索引设计对不对——要灌到真实数据量（当时灌了 5 万篇）再看。

同一个逻辑也适用于关注流：`EXPLAIN` 显示 JOIN 确实走了 `idx_user_time`（`rows=5`），但 `Extra` 里有 `Using temporary; Using filesort`——`ORDER BY` 跨 JOIN 需要建临时表再排序，**这才是数据量上来之后的瓶颈**。当前量级（`follow` 只有几行）根本看不出来。

### 7.16 凭据硬编码在源码里

原项目把 `user`/`passwd` 直接写在 `main.cpp` 里（上游是 `root`/`root` 这种演示占位符，无所谓）。我把真实口令放在那里之后，一旦公开就等于交出库口令。

改法是只从环境变量读（`MYSQL_USER` / `MYSQL_PWD` / `MYSQL_DB`），缺失时**直接报错退出，不做静默回落**——静默回落会让"忘了导出变量"表现为认证失败或连错库，排查成本远高于直接报错。真实口令只存在于被 `.gitignore` 忽略的 `run-local.sh` 里。

**核心认识**：靠"提交前记得改回来"是守不住的，因为这个文件此后每一次改动都可能把它带上去，而 git 历史里的口令很难清除。**要从结构上让它不可能发生**，而不是靠纪律。

## 9. 已知不足，以及被问到时的答法

被问到"你这个改动有什么问题"时，**不要说没问题**。下面三条如实说，反而最能证明你在认真做工程。

### 9.1 静态页吞吐比改造前低约 2.4 倍，根因未定位 ⚠️

先说清楚结论，再说清楚它为什么可疑：

- 四路交叉对照（新/旧 × `-g`/`-O2`，交替顺序、每档两轮）：新 123k、旧 305k pages/min。
- **`-O2` 对两边都只值 1.5%**（新 122872→124704，旧 302321→307412），所以差距与优化等级无关。
- 继续拆解：`c=1`（单连接、零并发压力）时新代码就已经慢 2.15 倍；每请求 CPU 时间两边几乎一样（服务端 0.22 vs 0.18 ms），而 `c=100` 时**整机只跑到 0.65/2 个核**。结论是"**不是算力不够，是每请求多等约 0.3ms**"。
- 已排除：`-O2`、结构体大小（新的反而更小）、系统调用数（`strace -c` 基本一致）、日志量（新的更少）、事件循环结构、`close_conn` 的排空 `recv`（用的确实是 `MSG_DONTWAIT`）。

**但这组数字必须打问号**：当时的记录里写着"7.6GB 内存"，而实测 `MemTotal` 只有约 1.9GB——也就是说**压测是在 `MemAvailable` 只剩 250~340MB、swap 已用 1.4G 的状态下跑的**。"服务端 CPU 时间几乎一样、整机只跑到 0.65/2 核、每请求多等 0.3ms"这三个特征**恰好都是内存/swap 停顿的特征**。

所以正确的说法是：

> 我做过一轮 A/B 对照，但事后发现两组数字是在内存饥饿的状态下测的，"2.4 倍"这个结论不能作为代码问题定论。下一步应该在内存充裕的机器上重测，如果仍然存在，再对 8 个 worker 线程做采样式调用栈统计——本机 `perf` 不可用（`perf_event_paranoid=4`），`gdb` 批量 attach 那条路也没走通。

**这样讲比给一个虚高的吞吐数字强得多**：它展示的是"我知道我的数据在什么条件下才可信"。

### 9.2 关注流与列表页的 `filesort`

`ORDER BY` 跨 JOIN 产生 `Using temporary; Using filesort`；列表页是 `type=ALL` 全表扫 + filesort（`idx_create_time` 存在，但排序列是 `(create_time, article_id)` 两列，优化器没选它）。当前数据量（几行到几十行）不体现，数据量上来后需要处理。**这是关系模型的固有代价，不是 bug。**

### 9.3 TLS 只存在于代理配置里

服务自身仍只说 HTTP（这是 6.1 的刻意选择）。要复现 TLS 验证，按 `deploy/README.md` 起 `deploy/nginx.conf` 即可。

## 10. 预演：高频追问

**Q：为什么用 epoll 而不是 select/poll？**
（这块是原项目的设计，如实说"这是原项目的实现，我读过"）`select`/`poll` 每次调用都要把整个 fd 集合从用户态拷进内核并线性扫描，连接数上千后 O(n) 的拷贝和扫描成为瓶颈；epoll 用内核里的红黑树维护 fd、就绪事件放到链表里，`epoll_wait` 的返回只与**就绪**的 fd 数相关。另外 `epoll_ctl` 一次注册长期有效，不需要每次调用都重新传整个集合。

**Q：ET 和 LT 的区别？你为什么用哪个？**
LT（水平触发）只要缓冲区还有数据就会持续通知；ET（边缘触发）只在状态变化时通知一次，因此**必须循环读到 `EAGAIN`**，否则数据会留在缓冲区里再也不被通知。ET 的效率更高（通知次数少），代价是必须配非阻塞 fd，且写侧要处理"没写完"的情况。原项目触发模式（LT/ET）由 `-m` 指定，反应堆模型（Proactor/Reactor）由 `-a` 指定，默认 Proactor。

**Q：线程池怎么避免惊群？**
（同样如实归给原项目设计）Linux 下 `epoll_wait` 的惊群问题在内核 4.5+ 已基本解决；同时主线程负责 `accept` 再分发给工作线程（Proactor），工作线程不直接 `accept`，天然避免了多个线程抢同一个连接。

**Q：事务里为什么要坚持用同一条连接？**
因为事务是**连接级**的状态。如果 `BEGIN` 在连接 A 上、`COMMIT` 在连接 B 上，事务会静默失效——不会有任何报错，但数据不一致。这个项目里还有个额外约束：线程池在调 `process()` 之前已经用 `connectionRAII` 取好一条挂在 `http_conn::mysql` 上了，业务代码再取第二条会占满只有 8 条的池子。所以 `db/transaction.h` 做成了 RAII，保证任何提前 `return` 都能回滚，且**从头到尾用的都是那一条预取的连接**。

**Q：XSS 为什么在服务端转义？前端转义不行吗？**
前端的转义只能防"渲染时"的 XSS，防不住**存储型** XSS 的入库；而且接口是公开的，攻击者可以直接 POST，绕过你的前端。服务端在**输出**时转义（而不是在输入时），是因为同一份数据可能有多种输出上下文（HTML、JSON、URL），在输入时转义会让"这份数据到底被转过几次"变得不可知，很容易变成双重转义。

**Q：`SameSite=Lax` 和 `Strict` 怎么选？**
`Strict` 更安全，但会让"从外部链接点进论坛"的第一次请求看起来像未登录（用户以为掉线了）。`Lax` 在"跨站请求不带 Cookie"这点上同样挡住了 CSRF（攻击者的页面发不出带身份的写请求），代价小得多。`HttpOnly` 防的是**XSS 偷 Cookie**，`SameSite` 防的是 **CSRF**——两者防的不是同一件事，所以都要有。

**Q：如果让你重做，你会怎么改？**
（准备好这个，几乎必问）三点：
1. 先建**持续集成**：那 316 项断言应该一开始就进仓库并挂在 CI 上，而不是放在 `/tmp` 里丢一次。
2. 凭据、日志级别这类东西应该**在第一次提交前**就确定，而不是等要公开的时候才回头清理。
3. 压测要**在同一台干净的机器上、固定环境**做，并且先记录环境指标（`MemAvailable`、swap 使用量、cpu 频率）再采数——这次的数据之所以不可信，就是因为环境没记准。
